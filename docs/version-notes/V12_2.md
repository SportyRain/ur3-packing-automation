## Why V12.x was created

V11.x reused the V10 installation while adding new state and new PLC behavior. That caused version/state drift: P2 EXTRA was not a real persistent V10 variable, TCP/I/O/gripper state was not cleanly versioned together, and runtime-generated approach IK could repeatedly block the cycle.

V12 separates the candidate into one consistent set:

- `UR3_PACKING_V12*.urp`
- `UR3_PACKING_V12*.script`
- `UR3_PACKING_V12*.installation`
- `UR3_PACKING_V12*.variables`

## Current V12.2 contract

- Active TCP: `Box_Gripper1`, centered `tool0 +Z 0.080 m`.
- Standard Control Box I/O:
  - DI7 = PLC START
  - DO0 = GRIP_A
  - DO1 = GRIP_B
  - DO7 = POINT_DONE
- PLC cycle: exactly **6 START/DONE transactions**.
- P1 and P2 are combined into one PLC transaction:
  - START -> HOME -> P1 APPROACH -> P1 PICK -> grip close -> P1 RETRACT -> HOME -> P2 APPROACH -> P2 BOTTOM HOLD -> P2 EXTRA HOLD -> DONE.
- P2 EXTRA HOLD is a real persistent P/Q point and is taught as **3/8**, immediately after P2 BOTTOM HOLD.
- Runtime `run_cycle()` performs **0 inverse-kinematics calls**.
- Approach IK is commissioning-only; successful approach pose + joint posture + clearance are persisted.
- General auto approach search: `100 -> 90 -> 80 -> 70 -> 60 mm`.
- P3 PRODUCT INSERT first attempts the required local-Z **70 mm** approach; if that is unreachable, V12.2 uses a manually taught persistent approach/backoff instead of blocking forever.
- Other general approaches also fall back to manual persistent teaching only if the full automatic clearance search fails.

## Runtime evidence / failures

### V12

V12 loaded far enough on the real pendant to run commissioning and stop with:

`P3 PRODUCT INSERT 70 mm approach is not reachable.`

This demonstrated that the fixed 70 mm generated approach was not reachable for the current taught P3 insert posture. V12.1 therefore changed P3 insert to allow a manually taught persistent approach/backoff.

### V12.1

Real PolyScope parser rejected the mixed-type list used by the commissioning helper:

`local r = [False, p[...], [joint...], 0.0]`

The error reported that a Boolean could not be mixed with Pose/list/float elements in that list.

### V12.2 fix

V12.2 removes the heterogeneous return/list completely.

- `commission_general_clearance()` returns only one `float` clearance.
- Pose and joint posture are computed and persisted separately by the caller.
- No mixed `BOOL + Pose + list + float` container remains.
- Known prior CB3 parser problems remain removed: no direct `abs()` call and no `getj()`.
